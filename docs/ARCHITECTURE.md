# Core API-v1 and C1 security foundation

## Status and limits

This document records a provisional API scaffold and C1–C5 runtime/security boundary. It does not freeze API v1 or establish Pro compatibility. The OpenAI Responses/File Search adapter is inert unless an explicit server-only fixture constant enables it. Core package versioning and API-major versioning are separate.

Future Pro registration must occur only after Core bootstrap, validate the Core API major and declared minimum Core package version, and fail closed when absent or incompatible. It must then register no public route and make no provider call. Standalone Core remains usable.

## Core-owned request boundary

Core owns the sole public POST /ncli/v1/chat route, credential resolution, transport selection, rate/budget ordering, profile readiness, completed-File-Search validation and public errors. No seam receives an API key, raw provider payload, retrieved source text, secret resolver, provider client, route registrar or mutable Core request object.

C1 registers an NCI-only activation/deactivation lifecycle. Activation creates fresh ncli_core_settings and a schema marker, then creates the prefixed ncli_core_rate_buckets table. Deactivation deliberately preserves NCI settings and rate data.

The only supported API-key source is the server-side NCLI_OPENAI_API_KEY_DEFAULT constant. Core never reads a key from an option, settings request or API request. Readiness remains unready until the default profile is enabled, that constant is present, the configured vector-store reference and corpus version are non-empty, and the current effective configuration has a passing administrator connection test. The stored diagnostic contains only `never`, `passed` or `failed`, a UTC test time and an opaque HMAC fingerprint; it never stores a secret, provider payload, vector-store reference, response, citation or retrieved text.

Public-safe error payloads are closed to seven codes: profile unavailable, invalid request, policy refusal, allowance exceeded, provider-safe failure, evidence failure and access required (CC-3; only for a protected non-default profile). They are deliberately generic.

The Core default profile is the only C1 profile. A disabled profile and every named non-default profile resolve to no profile; no request may fall back to Core from an unknown name.

## C2 workspace and presentation boundary

C2 adds a one-profile administrator workspace: Setup, Profile, AI and Corpus, Conversation, Appearance and Limits, Placement, Diagnostics and Help. It uses the Core capability/nonce guard, CoreSettings validation and escaped output. The settings page never renders a key, provider payload, retrieved text, file ID or vector-store identifier.

Core registers the ncli_interactive and ncli_limit_notice shortcodes and ncli/interactive block. It has Classic, Minimal and Dark panel styles. A historical `editorial` setting value is normalised to `dark` when settings are read or saved; it is not presented as a selectable style. The Core-only presentation fields are bounded title, headline, introduction, placeholder and footer labels, with a shortcode/block title taking precedence for one render. C3 sends a JSON request only to Core's route and keeps the browser transcript in page memory only; no transcript or turn is persisted.

The administrator workspace is a top-level, one-profile Core screen with NCI-specific masthead, bounded setup/readiness guidance, Core-safe tabs and a sticky save action. Its saved owner response guidance can shape response style and format only; Concise, Balanced and Detailed supply Core-defined detail baselines, while immutable retrieval, safety, privacy and disclosure rules always win. It never adds profile switching, authored question collections, contextual placement or an answer cache: those remain Pro-only. RC9 adds an optional, off-by-default conversation history with basic view and delete controls (see below); governance of that history remains a Pro capability. The public frame supplies only a session reset and loading/disabled states around the existing Core route and bounded answer output; it does not alter request payloads, transport ordering or validation. Answers may be rendered through a constrained, DOM-built Markdown subset (headings, paragraphs, lists, quotations, code blocks and basic emphasis). It never parses provider-returned HTML or turns Markdown links into browser navigation.

The Setup tab reconstructs the bounded four-step Core workflow: server-only `NCLI_OPENAI_API_KEY_DEFAULT` confirmation, vector-store/corpus configuration guidance, an administrator-only nonce/capability-protected File Search connection test, and published shortcode/block placement guidance. The test has no REST route or visitor output; it uses the selected Core transport with a fixed internal request, discards its answer/citations and passes only on a completed File Search result. It reserves only the existing global provider allowance. A reservation is released only before dispatch; attempted failures and timeouts remain accounted for and are not automatically retried.

## C3 mock retrieval boundary

The route first rejects malformed request shapes and attempts to override Core's default profile/preset. It then resolves the default profile without fallback, composes the non-negotiable Core policy, Core-defined detail baseline and bounded owner response guidance, checks readiness and calls its Core-owned transport. Owner guidance is a style-and-format preference only and cannot alter Core retrieval, safety, privacy, disclosure, provider-tool or route requirements. `DeterministicMockTransport` is enabled only by the boolean server constant `NCLI_CORE_MOCK_TRANSPORT`. `OpenAiResponsesFileSearchTransport` is selected when `NCLI_OPENAI_API_KEY_DEFAULT` is defined and non-empty, so no second setting is needed; the boolean `NCLI_CORE_LIVE_TRANSPORT` remains an optional explicit override (true forces live mode, any other defined value switches the provider off), and `NCLI_CORE_MOCK_TRANSPORT` takes priority for tests; it reads the key solely from `NCLI_OPENAI_API_KEY_DEFAULT`, sends a fixed Responses request to the OpenAI endpoint with File Search, uses the current Core vector-store setting, and permits one response up to 60 seconds without retry. Both values are supplied only to a disposable fixture environment. Without one of those explicit modes, Core selects an unavailable transport.

Every historical answer needs a completed File Search result. The adapter deliberately does not request File Search result text. Since CC-6 (NCI-CD-011) it keeps, from provider citation metadata, only the file reference and file name of each file citation as a bounded descriptor for an installed extension; everything else in the metadata is discarded. The result must carry current policy and corpus fingerprints. Public output is limited to the bounded answer. Provider IDs, citation metadata, retrieved text, provider payloads, secrets and diagnostics are never emitted. A policy refusal, invalid request, unavailable profile, provider failure and retrieval-validation failure use the closed public error set.

## C4 budget, privacy and resilience boundary

Before Core dispatches a transport request it reserves one visitor and one global provider allowance in the InnoDB-backed `ncli_core_rate_buckets` table. It locks the exact `(kind, scope_hash, period_start)` row in a transaction. The visitor scope is an HMAC under a server-only secret; Core never persists the address itself. No setup is needed: unless the site defines `NCLI_CORE_SCOPE_SECRET` in `wp-config.php` (which then takes precedence), the secret is derived from WordPress's own authentication salt, which is also kept in `wp-config.php` and never in the database. Rotating the salts, or defining the constant, only resets visitors' daily counts. If neither source exists the route reports itself unavailable (readiness state `missing_scope_secret`) rather than telling visitors their allowance is used up. Forwarded-client headers are ignored unless `REMOTE_ADDR` is in the explicit `NCLI_CORE_TRUSTED_PROXY_CIDRS` CIDR allowlist.

The day boundary is UTC midnight. A reservation released before provider dispatch restores allowance. Once dispatch is attempted, Core retains the reservation on timeout/ambiguous failure and never retries automatically. A returned answer that fails retrieval validation remains accounted for because provider work was attempted. Core has no answer cache of its own; an installed extension may supply one through the cache seam (CC-4).

On its own Core emits no public source links or citation metadata, so its public panel cannot turn a retrieved citation into a browser navigation or internal-network request path. The detailed lifecycle and privacy record is `docs/PRIVACY-LIFECYCLE.md`.

## Provisional seams (five original, one added in CC-3)

| Seam | Contract | Bounded intent | Fail-closed rule |
| --- | --- | --- | --- |
| Profile resolution | ProfileResolverV1 | Resolve an explicit non-default profile identifier (wired in CC-2). | Empty, malformed, unknown or disabled identifiers never fall back to Core's corpus. |
| Supplementary chronology | ChronologyProviderV1 | Offer at most 20 bounded chronology facts. | Invalid facts are rejected; chronology cannot set corpus/provider/instructions. |
| Eligible cache | AnswerCacheV1 | Lookup/store only a fully fingerprinted eligible answer. | Missing, malformed or mismatched values are cache misses. |
| Completed public turn | CompletedTurnRecorderV1 | Receive only a successfully validated cache/provider turn. | Core does not invoke it for refusals, deterministic responses, diagnostics or failed delivery. |
| Workspace extension | WorkspaceExtensionV1 | Supply fixed permitted workspace screens only. | Unknown screens and missing Core capability/nonce checks are rejected. |
| Viewer access (CC-3) | ViewerAccessV1 | Decide whether the current viewer may use a non-default profile. | Any exception, wrong type or invalid decision is a denial; the default profile never reaches it. |

The registry permits one implementation for each known seam and rejects unknown, mismatched and duplicate registrations. It is a pure contract mechanism, not WordPress integration.

### Extension handshake (CC-0)

Core declares `NCLI_CORE_API_MAJOR` (1) and `NCLI_CORE_API_MINOR` (1). The minor number rises when an existing contract changes shape incompatibly with an earlier minor. The registry also publishes `capabilities()`, a list of the extension capabilities this build really implements (currently `handshake`, `workspace_hosting`, `profile_resolution`, `viewer_access`, `supplementary_chronology`, `eligible_answer_cache`, `completed_public_turn`, `conversation_context`, `evidence_citations`, `evidence_screen`, `panel_colours`, `panel_events` and `conversation_governance`); a name is added in the Core change that implements it, so an extension gates on capabilities, not on guesses from the version. An extension must check Core's package version, the API major and minor and every capability it needs on `ncli_core_api_v1_ready`, and register nothing if any is missing. `implementation($seam)` lets Core retrieve a registered implementation (null when absent) so Core can fail closed; Core behaviour is unchanged when nothing registers.

### Chronology and answer cache (CC-4)

**Chronology.** `ChronologyProviderV1::factsFor()` is consulted through `ProfileDirectory::chronology()` for every profile, including the default. Core accepts only a list of at most 20 `ChronologyFactV1` values; an exception, a non-list, a wrong entry type or more than 20 entries means no facts, never a partly trusted list. Facts are added to the instructions as a delimited section (`--- BEGIN/END CHRONOLOGY RECORDS ---`, one `date | label | summary` line per fact, flattened to one line with control characters removed and dash runs collapsed so a fact cannot forge a boundary), described as supplementary owner-verified facts rather than instructions, placed before owner guidance, with the priority reminder still last. They are part of the policy fingerprint, so any change to a fact invalidates cached answers; with no facts the instructions and every fingerprint are byte-for-byte what they were. The connection test does not include them.

**Answer cache.** After access and readiness checks, and before any budget reservation, Core builds a `CacheKeyV1` (SHA-256 of the case- and space-normalised question, profile id, policy fingerprint including chronology, an answer-source fingerprint covering corpus version, vector store and model settings, an `open` access-state fingerprint and the preset) and asks `AnswerCacheV1::lookup()`. Core re-validates a hit (non-empty, at most 5,000 bytes, no control characters; an exception or wrong type is a miss) and returns it as an ordinary answer: no provider call, no visitor or provider allowance, and the turn is recorded in Core's history like any other. After a provider answer that passes evidence validation, Core offers it with `store($key, $answer, $question)`; the extension decides whether to keep it, and a failure there never changes the response. Answers that fail validation are never offered. The cache is skipped entirely for an access-controlled (restricted) profile, and Core sends no earlier-turn context yet, so every request is currently eligible; once earlier turns are sent (CC-5), requests that carry context will bypass the cache. The key holds no question text; the question reaches the extension only through `store()` so an owner can review it.

### Profile hub (CC-10c)

With an extension that registers `profile_editor`, NC Interactive opens on a Profiles page: the default profile and every extension profile in one table with availability, access and a connection-test status that Core computes itself (`ProfileDirectory::status()`, the same readiness rules as the public panel), an Open link, a Test connection button and an Add profile link. Opening a profile shows the same tabbed workspace Core uses for its own profile (`ProfileFieldRenderer::profileRows()` draws the rows), with a title strip, a profile switcher and a sticky save bar linking back to all profiles. Core's `?tab=` addresses still open the default profile. Without an editor nothing changes.

- **`ProfileEditorV1`** stores profiles: `summaries()`, `values()`, `create()`, `save()`, `delete()`, `limit()`. Core builds a `ProfileEditV1` from the posted form (validated by `ResolvedProfileV1`, `ModelSettings` and `PanelAppearance`) and only then calls it; a stored vector-store reference is never handed back (null means keep). A throwing, malformed or default-id-listing editor yields an empty list, so Core shows its own profile alone.
- **`ProfileWorkspaceV1`** adds `ProfileSectionV1` blocks (a permitted tab, a key, a title) to a profile's tabs, drawn beneath Core's own fields. Core issues each section a nonce with action `ncli_ext_<key>`. Questions & sharing and Cached answers exist as tabs only when a section targets them. A failing section is replaced by a generic notice. Sections apply to the default profile too.
- Each tab saves only its own fields; a profile's model and appearance blocks become its own only when AI & Corpus or Appearance & Limits is saved, until then it inherits the default profile's.
- Per-feature pages an extension no longer declares (`ncli-ext-*`) redirect to the Profiles page. The Settings menu entry is renamed Profiles while the hub is active.

### Site pages and hub layout (CC-11)

While the hub is active (a registered `profile_editor`) NC Interactive's menu is Profiles, Conversations, Settings and a Help entry that opens the Help tab of Settings. The extension's `settings` and `archive` screens are no longer menu entries: `ExtensionScreens::bodyHtml()` returns a screen's body (with a Core-issued nonce, and a generic notice on failure) for Core to host, `settings` under Settings > General and `archive` as the Governance tab of Conversations. `SiteSettingsPage` (slug `ncli-settings`) holds the daily provider allowance and Delete data on uninstall, which leave the default profile's tabs, and Help (`HelpRenderer`, the same content as before). Old `ncli-ext-*` addresses and the default profile's Help tab redirect while the menu is built. The Profiles table shows Tag, Connection test and Last tested in separate columns, and the profile switcher and All profiles link sit in the title strip of every profile workspace. Capability: `site_pages`. Without an extension none of this exists and Core's single Settings page is unchanged.

### Per-profile model and appearance (CC-10b)

`ResolvedProfileV1::configured()` takes two optional blocks. `model` (all of id, reasoning_effort, retrieval_depth, max_output_tokens, timeout_seconds) and `appearance` (any of panel_width, accent_color, show_credit). Left out (null), the profile inherits the default profile's values exactly as before. The value object checks only structure; Core's `ProfileRuntime::fromResolved()` checks the values with `ModelSettings::validate()` (the same rules as Core's own settings) and `PanelAppearance`, and any invalid value makes the profile unavailable rather than falling back to the default model. The model block feeds the connection-test fingerprint and the answer-cache source fingerprint, so changing it requires a new test and misses old cached answers. The site-wide provider daily budget stays one shared setting.

### Admin look of extension screens (CC-9)

`ExtensionScreens` gives every extension screen the same chrome as Core's own screens: it loads `assets/css/admin.css` on those pages, draws the masthead and a tab bar (a link back to Settings, then one tab per screen the extension declares, the current one marked), and wraps the extension's body in `section.ncli-admin__tab-panel.ncli-admin__extension`. The extension supplies only the body and should use Core's `ncli-admin__*` classes (form table, field row, section row, save bar, inline form, pre-wrapped text, check list) instead of inline styles. These class names are an informal contract: removing one is a visual regression for any installed extension. A failing extension still shows the masthead, tabs and a generic notice, never a panel.

### Conversation governance (CC-7)

`ConversationGovernanceV1` lets an installed extension add export, per-profile recording and retention, and scoped erasure on top of Core's own history without a second archive.

- **Archive.** After extensions register, Core calls `attach()` with a `ConversationArchiveV1` (`GuardedConversationArchive`), never the table. Every call requires `manage_options` (checked by Core itself), validates its arguments (profile ids, real `Y-m-d` dates in UTC, inclusive, start not after end) and works in bounded pages of at most 500: `count`, `page` (oldest first after an id cursor, returning `ArchivedTurnV1`: id, conversation id, profile, time, question, answer) and `delete`, which always requires one profile and a limit. There is no delete-everything call and no visitor identifier, because none is stored. `WordPressConversationStore` gained criteria methods through a separate `ConversationCriteriaStore` interface so existing `ConversationStore` implementations are unaffected; their SQL always binds values through `$wpdb->prepare()`.
- **Recording.** `recordingFor($profileId)` returns true or false to override Core's "record history" setting for that profile, or null to defer to it. An exception or non-boolean defers to Core.
- **Retention.** `retentionOverrides()` returns `profile id => 0|30|90|365`. A listed profile follows its own schedule (0 keeps until deleted); every other profile follows Core's. Core's daily purge applies profile schedules first, then its own schedule excluding the listed profiles; with Core set to keep forever only a listed profile with a shorter schedule is purged. Any fault, malformed key or value, or more than 100 entries yields no overrides, so Core's schedule applies to everything: a failure can only shorten retention, never lengthen it. Deactivating the extension has the same effect.
- **Not covered.** Restored database backups can reintroduce erased records; erasure and any audit log are the extension's responsibility.

### Panel colours and panel events (CC-8)

**Colours.** `PanelColoursProviderV1::coloursFor($profileId)` may return a `PanelColoursV1`: up to six `#rrggbb` values (`question_background`, `question_text`, `question_border`, `answer_background`, `answer_text`, `answer_border`) for the default or a named profile. Core re-validates them, never emits free-form CSS, and writes only fixed custom properties on the panel root (`--ncli-q-bg`, `--ncli-q-ink`, `--ncli-q-rule`, `--ncli-a-bg`, `--ncli-a-ink`, `--ncli-a-rule`), read by `public.css` with the style's own colours as fallback. A block's background and text are used only if the text reaches a 3:1 contrast against the background (against the style's own colour for whichever one was not chosen); otherwise both are dropped and the style's colours stay. Borders are used whenever valid. Any invalid value makes Core ignore the whole set; an exception, null or a wrong type changes nothing. The accent colour remains a Core setting.

**Panel events and markup contract.** Each panel root carries `data-ncli-panel`: the profile id for the default (`default`) or a resolved and permitted named profile, and `unavailable` for anything else (an id is never echoed for a profile the viewer cannot use). Another script may dispatch a bubbling `CustomEvent` on an element inside a panel: `ncli:ask` with `detail.question` fills the panel's textarea and submits its form, and `ncli:prefill` fills it and moves focus without sending. Both do only what a visitor could do by typing: the text goes through the same form, route, limits and validation, is ignored if longer than 2,000 characters, blank or not a string, and is ignored while the panel is busy, disabled or unavailable. There is no automatic sending on page load; a shareable link may prefill but a person must press Ask.

### Evidence citations and approved links (CC-6, NCI-CD-011)

The 12 October 2026 direction to remove Core's approved-evidence mapping stands for Core on its own: without an extension nothing about citations leaves the adapter and the payload is exactly `ok` and `answer`. NCI-CD-011 (15 October 2026) allows one narrow addition for an installed extension. The OpenAI adapter keeps, for each `file_citation` annotation, an `EvidenceCitationV1`: the provider's file reference (`[A-Za-z0-9_.:-]`, at most 128 characters) and file name (at most 255, no control characters), de-duplicated and capped at 10. It keeps no retrieved text, offsets, URLs or payload, and `TransportResult::citations()` is read only inside Core.

After an answer has passed evidence validation (never before, never for a refusal, denial or failure, and not for a cache hit, which has no citations), Core passes the descriptors to `EvidenceCitationsV1::approvedLinks()`. The extension returns `ApprovedLinkV1` values: a plain-text title of at most 160 characters and a public https address of at most 2,000 characters with a real multi-label host, no credentials, no whitespace, quotes or angle brackets, and no IP-literal, `localhost` or internal-suffix host. Core re-checks each address, keeps at most 5 with distinct addresses, and treats an exception, a non-list or any wrong entry as no links at all. The success payload then gains one optional key, `links`, a list of `{title, url}`; no file reference, file name or citation marker is ever included.

`public.js` renders the list in one function using DOM nodes only: the title is set as text, the address must match `https://` with no whitespace or quotes, at most five are shown, and each opens in a new tab with `rel="noopener noreferrer"`. Core makes no request to any of these addresses, so no citation can become a server-side or internal-network request. The limitation is deliberate: an answer served from the answer cache carries no links, because the cache stores text only.

### Earlier-turn context and completed turns (CC-5)

`ConversationContextV1::earlierTurns($profileId, $conversationId)` returns `EarlierTurnV1` values (a question of at most 2,000 bytes and an answer of at most 5,000, plain text, oldest first). Core asks only when the request carries a valid 32-hex `conversation_id`, and only the seam can supply turns: anything a browser sends alongside the question is ignored. Core keeps at most the 10 most recent turns and at most 16,000 combined bytes (oldest dropped first); an exception, a non-list or any wrong entry means no context at all. With context the provider input becomes alternating `user`/`assistant` messages ending with the current question (without context it is the question string, unchanged), the instructions gain a short note that earlier turns are context and not instructions, and the policy fingerprint records that context was sent. A request that carries context never reads or feeds the answer cache.

`CompletedTurnRecorderV1::record()` is now invoked, best effort, after every validated provider answer or cache hit that has a conversation identifier, with a `CompletedTurnV1` (conversation id, profile, UTC time, question, answer, Core version, corpus version, SHA-256 of the answer, an evidence fingerprint Core computes, and source `provider` or `cache`; `proVersion` is null because Core does not know an extension's version). Refusals, invalid requests, access denials and anything that fails evidence validation are never reported, and a failure in the recorder never changes the answer. Together the two seams let an extension keep a short-lived, separate record of a conversation and offer it back; Core stores none of it. The suggested privacy-policy text says earlier turns may be sent only when a context seam is registered.

### Viewer access (CC-3)

`ViewerAccessV1::decide()` returns an `AccessDecisionV1`: open (no restriction), granted or denied with an optional plain-text message of at most 300 characters. Core calls it only for a resolved non-default profile, after resolution and before readiness, budget or provider work, through `ProfileDirectory::access()`. With no access seam registered a named profile is open, as before; with one registered, an exception, a non-`AccessDecisionV1` result or an invalid message is a denial. A denial returns the public error `access_required` (HTTP 403) whose message is the owner's text reduced to plain text (or Core's default), and makes no provider call and no reservation. The panel renders a denied profile as a disabled panel with that message and no profile marker, and a restricted profile's page sets `DONOTCACHEPAGE` and no-cache headers. The public client sends `X-WP-Nonce` (WordPress's `wp_rest` nonce, exposed as `NCLI_CORE_CHAT.nonce`) only for panels with a named profile, so the REST layer can identify a signed-in viewer; the default panel's request is unchanged. A page cache that serves one viewer's nonce to another produces a failed request, not a grant. Core never caches a restricted profile's answers because Core has no answer cache.

### Workspace hosting (CC-1)

When a `WorkspaceExtensionV1` is registered, Core adds one submenu page under "NC Interactive" for each screen it declares (`ncli-ext-<id>`). The title comes from a Core-owned label table, never from the extension. Every request is checked for `manage_options` before the extension is called; Core creates a per-screen nonce (action `ncli_ext_<id>`) and passes it in `WorkspaceContextV1` together with the screen id and nonce action. An extension's own form handler must verify that nonce and `manage_options` itself; Core does not intercept it. The extension's output is buffered: if `screens()` or `render()` throws, or returns a screen object of the wrong type, the screens are hidden or the body is replaced by a generic notice and the visitor-facing route is unaffected. Screen ids remain limited to the `WorkspaceScreenV1` identifiers: profiles, chronology, questions, collections, cache, archive and (from the capability `evidence_screen`) evidence.

### Profile resolution (CC-2)

Core's `ProfileDirectory` is the only place a profile id becomes a profile Core will answer from. The `default` id always comes from Core's own settings and is never offered to an extension. Any other id is resolved only through a registered `ProfileResolverV1`, and every doubt (no resolver, exception, wrong type, an id that differs from the one asked for, disabled, no configuration, out-of-bounds configuration) means unavailable. There is never a fallback to the default corpus. Without a resolver, a non-default id remains `invalid_request`, exactly as before.

An extension supplies configuration through `ResolvedProfileV1::configured()`: vector-store reference, corpus version, owner guidance, response preset, wording, panel style and per-visitor daily limit. Each is bounded in the value object and again by Core. The policy and corpus fingerprints are computed by Core from that configuration; a profile built with the legacy constructor carries none and cannot be answered from. A named profile inherits Core's model, retrieval, timeout and provider settings, and the site-wide provider allowance stays shared; its visitor allowance is counted in a separate bucket per profile (the default profile's bucket is unchanged).

Each named profile needs its own passing connection test. Core runs it (`Admin/ProfileConnectionTest`, `admin-post` action `ncli_test_profile`, verified with the extension screen's Core-issued nonce and `manage_options`) and stores only `passed`/`failed`, a UTC time and an opaque HMAC fingerprint per profile id in the Core-owned option `ncli_core_profile_tests`. An extension cannot write or forge it. Changing anything that feeds the fingerprint (vector store, corpus version, guidance, preset, Core version, model settings) makes the record stale. The shortcode and block accept `profile`; the panel then carries `data-ncli-profile`, the public client sends `profile_id`, and an unresolved or untested profile renders Core's disabled, generic panel without echoing the id. History records the profile id and that profile's corpus version.

## Value boundaries

- ProfileIdV1 accepts only explicit lower-case IDs matching ^[a-z0-9][a-z0-9_-]{0,63}$.
- CacheKeyV1 includes the question digest, profile ID, policy fingerprint, corpus fingerprint, access-state fingerprint and response preset. Every field participates in identity.
- CompletedTurnV1 carries the question, answer, Core version, optional Pro version, corpus version and non-secret fingerprints as a contract payload. It does not store anything. Core's own conversation log (below) does not use this contract.

Pro does not exist yet. The owner-approved Pro archive-governance policy remains documented in the canonical NCI context pack and applies to the Core-owned table below: disabled until explicitly configured; 30/90/365 days or deliberate indefinite retention; question/answer plus per-turn Core/app, Pro-if-active and corpus versions; scoped erasure; and disclosure that restored backups may reintroduce erased records and require scoped re-erasure.

## RC9 conversation history and administration (owner decision of 15 October 2026)

Core now owns an optional conversation history. This deliberately reverses the earlier position that any archive was Pro-only; the decision is recorded in `progress.md` as NCI-CD-010. Pro is expected to extend Core's table and screens with governance (export, retention schedules, per-profile scope, audited bulk erasure) rather than create a second archive, so a turn is recorded exactly once.

- **Storage.** `ncli_core_conversation_turns` (InnoDB, created through `dbDelta`) holds an opaque 32-hex conversation identifier, the profile identifier (`default`), the displayed question and answer, the Core version, the corpus version, the policy fingerprint and a UTC timestamp. It stores no address, account, cookie, header, provider payload, citation or retrieved text. Schema marker `ncli_core_schema_version` is now 2, and `Plugin::boot()` creates the table for sites upgraded from an earlier candidate without re-activation.
- **Recording.** `ChatService` calls `ConversationRecorder` only after a fully validated provider answer and only when the owner has enabled logging (default off). The write is best-effort; any failure is swallowed so the public response is unchanged. Refusals, invalid requests, unavailable profiles and every provider or evidence failure are never stored, and administrator connection tests never are.
- **Grouping.** The public client sends an optional `conversation_id`, generated in memory per page session and discarded on Reset. The route accepts only 32 lower-case hexadecimal characters; any other value makes the request invalid. It groups turns and has no other effect.
- **Retention.** A daily scheduled event removes turns older than the owner's period (30, 90, 365 days or indefinite; 90 by default once enabled). It runs whether or not recording is currently on.
- **Administration.** The top-level menu is "NC Interactive" with Settings and Conversations entries. The Conversation tab holds the recording, retention and uninstall settings and links to the Conversations screen, which lists conversations, shows one in chronological order and deletes one, several or all (all requires a separate confirmation step). Every action needs `manage_options` and a nonce; visitor text is escaped on output.
- **Uninstall.** `uninstall.php` removes nothing by default. If the owner has enabled "Delete data on uninstall" it removes exactly the NCI settings and schema options, the `ncli_core_rate_buckets` and `ncli_core_conversation_turns` tables and the purge event, per site on multisite.
- **Public appearance.** Panel width, an accent colour (always applied in every style and at every width; if it has under 3:1 contrast with the panel background the button gains an edge and the focus outline keeps the style colour), an editable unavailable message and an opt-in "Powered by NC Interactive" link are stored in `ncli_core_settings`. None of them changes the policy or connection fingerprint.
- **Earlier-turn context.** Core itself sends only the current question to the provider. An installed extension can supply bounded earlier turns through the context seam (CC-5, below); Core's route remains the sole provider caller.
