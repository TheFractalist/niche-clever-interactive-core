## Local `1.0.3` progressive-answer candidate cycle — 27 October 2026

Core has a default-on `streaming.progressive` setting and a bounded `presentation.processing_message`, whose default is `Receiving response…`. The global switch belongs to the default profile. Named profiles use the existing additive API-v1 presentation map: a blank processing message inherits the Core default; a populated value overrides it only for that profile. `InteractivePanel` renders the effective value only as an escaped per-panel data attribute, so it is safe for a mixed-profile page. This did not add a Premium provider path, public route, credential seam or direct HTTP method.

The Responses adapter again uses WordPress's documented `http_api_curl` hook, but only while its fixed Core-owned URL is in flight. The callback ignores other URLs, sets only `CURLOPT_WRITEFUNCTION`, passes successful chunks through the existing bounded reader, and is removed in `finally`. Its two cURL-handle calls retain narrow, reasoned WPCS exceptions for the documented WordPress hook; Core does not call `curl_init`, `curl_exec` or equivalent standalone functions. When WordPress's selected HTTP transport does not invoke the hook, the same request's retained SSE body is sent to the reader once after completion. That fallback creates neither a duplicate provider request nor a second budget reservation. Streamed text is still display-only and retrieval-gated; the only final answer remains the fully completed Core-validated provider result.
